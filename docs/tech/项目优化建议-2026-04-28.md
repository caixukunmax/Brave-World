# 项目优化建议（2026-04-28）

## 1. 结论摘要

当前项目已经具备明确的模块拆分基础：

- 服务端按 `Common / Services / Database / Proto / Tables / GameLogic / Host` 拆分。
- 协议与配置表已独立到 `protocols/`、`tables/`，方向是对的。
- 关键玩法已有设计文档沉淀，说明团队已经有“文档先行”的意识。

但从工程化视角看，当前最值得优先优化的不是玩法代码本身，而是下面四类基础能力：

1. 自动化验证不足，改动回归风险高。
2. 构建入口分散，跨端联调成本偏高。
3. 生成物、源码、运行产物边界不够清晰，影响维护效率。
4. 规范与总览文档不完整，新人接手和长期演进成本会持续上升。

建议优先级：

- `P0`：测试与 CI、统一构建入口、生成物边界治理。
- `P1`：配置与依赖统一、日志与可观测性、文档补全。
- `P2`：目录命名一致性、脚本跨平台化、进一步的架构解耦。

---

## 2. 当前观察到的主要问题

### 2.1 自动化测试体系基本缺位

现状证据：

- 服务端 `servercsharp/src/` 下没有独立测试项目。
- 仓库内未发现 `.github/workflows/`。
- 当前可见的“测试相关”内容主要是客户端工具性质文件，如 `clinetcsharp/tools/TestClient/`，还不是稳定的回归测试体系。

影响：

- 玩家移动、战斗、协议、配置表这些高耦合链路，一旦改动，容易出现“局部修好，其他路径回归”的问题。
- 现在的验证方式更依赖手工运行 `restart.bat` 或实际联调，反馈慢，且难覆盖边界情况。

建议动作：

1. 新增服务端单元测试项目，优先覆盖纯逻辑模块：移动状态机、碰撞判定、战斗结算、消息路由。
2. 为协议生成、表生成增加最小冒烟测试，至少校验“生成成功 + 关键文件存在 + 服务端可加载”。
3. 建立一条最小 CI：`tables build -> protocols build -> dotnet build -> tests`。

预期收益：

- 把“改了能不能发”从经验判断，变成命令级确认。
- 后续做数值改动、协议扩展、AI 逻辑调整时，回归成本会明显下降。

---

### 2.2 构建入口分散，跨模块协作成本高

现状证据：

- 根目录 `package.json` 只有一个依赖，没有承担 workspace 级编排职责。
- `protocols/package.json`、`tables/package.json` 各自维护构建脚本。
- 服务端依赖 `servercsharp/build.bat`、`servercsharp/restart.bat`、`servercsharp/build_and_restart.bat` 串联表、协议、服务重启。

影响：

- 当前构建链路以手工记忆为主，不同人可能走不同脚本。
- 一旦后续增加客户端构建、协议校验、测试命令，入口会继续分叉。
- 批处理脚本适合本机开发，但不利于 CI 和跨平台复用。

建议动作：

1. 在仓库根目录建立统一任务入口，例如：`build:all`、`dev:server`、`verify`。
2. 把现在分散在 `.bat` 中的步骤抽象为可复用命令链，批处理脚本只做“Windows 快捷入口”。
3. 优先让“验证”与“启动”分离，避免每次都必须 `kill + rebuild + run`。

预期收益：

- 开发、联调、CI 使用同一套命令语义，减少流程歧义。
- 后续接入 VS Code task、GitHub Actions、预提交钩子会更顺。

---

### 2.3 生成代码与源码边界不清晰

现状证据：

- 协议生成代码位于 `servercsharp/src/GameServer.Proto/generated/`。
- `servercsharp/src/GameServer.Proto/` 下同时存在 `generated/`、`bin/`、`obj/`。
- 搜索时容易命中 `servercsharp/src/GameServer/bin/Debug/net8.0/` 下的运行产物和生成内容。

影响：

- 搜索结果噪音大，排查问题时容易看错文件。
- 生成文件与手写代码距离过近，后续更容易发生“误编辑生成物”或 diffs 过大。
- 运行产物混在 `src/` 视角里，不利于维护者快速识别“哪些是源代码，哪些是构建结果”。

建议动作：

1. 明确约定：生成代码统一进入专门目录，并在文档中声明“禁止手改生成物”。
2. 为 IDE 和搜索工具补充排除策略，默认排除 `bin/`、`obj/`、运行时导出目录。
3. 评估是否把 proto 生成结果进一步收敛到更明确的 `Generated/` 或构建输出目录，再由项目引用。

预期收益：

- 搜索、Review、排查问题的效率会明显提高。
- 减少“改对文件还是改错文件”的低级失误。

---

### 2.4 工程规范缺少仓库级统一配置

现状证据：

- 仅发现 `clinetcsharp/.editorconfig`，未发现仓库级 `.editorconfig`。
- 未发现 `Directory.Build.props` 或 `Directory.Build.targets`。
- 各 C# 项目的包版本分散写在各自 `.csproj` 中。

影响：

- 代码风格、Nullable、分析器、警告级别等很难统一收敛。
- NuGet 版本升级时，需要逐个项目维护，容易漂移。
- 长期看会增加多人协作的摩擦成本。

建议动作：

1. 在仓库根目录补一个统一 `.editorconfig`。
2. 通过 `Directory.Build.props` 统一 C# 语言版本、Nullable、TreatWarningsAsErrors 策略、分析器级别。
3. 逐步把常用包版本集中管理，避免多个项目各自漂移。

预期收益：

- 新文件默认遵循同一规范。
- 代码审查讨论会更多聚焦业务问题，而不是格式与低层约定。

---

### 2.5 文档有玩法深度，但缺少项目级总览

现状证据：

- 根目录已有 `docs/design/`，客户端也有 `clinetcsharp/docs/`。
- 现有文档更偏“单个系统设计”或“客户端使用说明”，例如移动、战斗、面板、登录流程。
- 当前缺少一份从仓库层面解释“协议、配置表、客户端、服务端如何协同”的总览文档。

影响：

- 新人很难在 10 分钟内理解“改协议要改哪里、改表要跑什么、客户端和服务端的数据边界是什么”。
- 当问题横跨表、协议、服务端逻辑、客户端表现时，排障路径不够直观。

建议动作：

1. 新增一份项目架构总览文档，说明四条主链路：`表 -> 生成 -> 服务端加载`、`proto -> 生成 -> 客户端/服务端通信`、`客户端预测 -> 服务端权威`、`本地调试 -> 重启验证`。
2. 给每条链路配一个“常见改动 checklist”。
3. 将“高风险约束”集中记录，例如：消息字段不能随便改编号、配置表变更要同步验证客户端/服务端、客户端预测不能突破服务端权威。

预期收益：

- 降低认知切换成本。
- 把一些隐性知识从“靠口口相传”变成文档资产。

---

### 2.6 依赖与包管理存在碎片化趋势

现状证据：

- `protocols/`、`tables/` 都是独立 npm 包，并各自带 `node_modules/`、`package-lock.json`。
- 根目录 `package.json` 目前没有承担 monorepo 级依赖治理。

影响：

- Node 侧工具链升级容易分散维护。
- 同一类工具如果后续扩展到更多目录，依赖版本可能继续漂移。

建议动作：

1. 评估采用 workspace 方式统一管理 Node 子项目。
2. 若暂不做 workspace，也建议先统一 Node 版本要求、安装流程和常用脚本命名。
3. 在 README 或架构总览中写清楚：哪些目录需要单独 `npm install`，哪些命令必须从对应目录运行。

预期收益：

- 降低“本机能跑、别人机器不能跑”的环境差异。
- 后续接 CI 时更容易复用缓存与脚本。

---

### 2.7 可观测性还有提升空间

现状证据：

- 服务端已有 Serilog，且有 `servercsharp/logs/` 和 `watch-logs.ps1`，说明日志基础已经具备。
- 但从仓库结构上看，还缺少对“关键业务链路日志”和“故障定位入口”的统一说明。

影响：

- 出现跨端问题时，容易陷入“客户端看动画、服务端看消息、表里看配置”三头切换。
- 没有明确的事件编号、链路标签或关键字段标准，后期排查复杂玩法会越来越慢。

建议动作：

1. 统一关键链路日志字段，例如 `PlayerId`、`MapId`、`MsgId`、`Action`、`DurationMs`、`Result`。
2. 为移动、战斗、登录、切图等核心流程补“可观测性约定”。
3. 补一份日志排查手册，说明遇到常见故障优先查哪些文件和哪些关键字。

预期收益：

- 把日志从“记录输出”升级成“定位工具”。
- 对复杂联调问题的排查速度会更稳定。

---

### 2.8 部分命名与目录约定可以更严谨

现状证据：

- 客户端目录名为 `clinetcsharp/`，存在明显拼写偏差。
- 当前仓库是多技术栈混合项目，目录命名一旦不稳定，后续脚本、文档、自动化配置都会被放大影响。

影响：

- 新人理解成本增加。
- 后续编写自动化脚本、文档、搜索规则时更容易出现“名字记错”的问题。

建议动作：

1. 先在文档中统一口径，明确客户端目录即 Godot C# 客户端。
2. 真正重命名目录放到后续专项里做，避免一次性改动波及脚本、工程文件、文档引用。

预期收益：

- 短期先止损，长期再治理。

## 3. 建议的落地顺序

### 第一阶段：先补工程底座（建议 1~2 周）

目标：把“是否安全可改”这件事建立起来。

建议优先做：

1. 建立服务端测试项目。
2. 建立最小 CI。
3. 建立统一验证入口 `verify`。
4. 给仓库补 `.editorconfig` 和 `Directory.Build.props`。

这是投入产出比最高的一阶段。

### 第二阶段：优化构建与生成链路（建议 1 周）

目标：把“表、协议、服务端”的协同改造成本降下来。

建议优先做：

1. 统一根目录命令入口。
2. 规范生成物目录和搜索排除规则。
3. 补全架构总览与改动 checklist。

### 第三阶段：做长期治理（按需推进）

目标：降低未来 3~6 个月的维护摩擦。

建议逐步推进：

1. Node 依赖工作区化。
2. 日志与排障文档标准化。
3. 目录命名和脚本跨平台化。
4. 持续评估服务端模块边界是否还需要进一步解耦。

---

## 4. 我认为最值得先做的三件事

如果当前时间有限，只做三件事，我建议按这个顺序：

1. **补服务端测试 + 最小 CI**
   这是收益最高的基础设施，没有它，后面的重构和扩展都更危险。

2. **统一构建/验证入口**
   让所有人都用同一套命令，减少环境差异和操作偏差。

3. **补项目级架构总览文档**
   当前玩法文档已经不少，但缺的是“把整个项目串起来”的那一层。

---

## 5. 补充判断

这个项目的核心问题，不是“代码写得乱”，而是**工程底座还没有完全跟上项目复杂度增长**。

当项目同时包含：

- Godot C# 客户端
- C# 服务端
- Proto 协议生成
- Luban 配置表生成
- 多份设计文档

它已经不是一个单体 demo，而是一个小型多端协同项目。此时继续主要依赖手工脚本和人工回归，后面每增加一个系统，维护成本都会呈非线性上升。

所以优化重点应该先放在：

- 降低回归风险
- 降低协作歧义
- 降低认知负担

而不是先追求局部代码“更优雅”。
