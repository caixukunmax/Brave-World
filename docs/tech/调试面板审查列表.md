## 1. 概述

调试面板（DebugPanel）是游戏内按 F12 打开的配置面板，包含 6 个 Tab：地图、玩家、怪物、NPC、系统、UI。支持保存/加载配置、预设管理。

### 文件清单

| 文件 | 行数 | 职责 |
|------|------|------|
| `DebugPanel.cs` | ~230 | 主文件：生命周期、tab 协调、F12 快捷键 |
| `DebugPanel.Config.cs` | ~470 | 配置保存/加载/预设/迁移 |
| `DebugPanel.DynamicUI.cs` | ~100 | 预设区 UI 创建 |
| `DebugPanel.Handlers.cs` | ~40 | 面板级事件处理（保存/放弃） |
| `DebugPanel.Nodes.cs` | ~30 | 节点初始化 |
| `DebugPanel.Undo.cs` | ~15 | 撤销系统（已禁用，no-op stub） |
| `DebugPanelTab.cs` | ~288 | Tab 基类：生命周期、辅助方法 |
| `DebugPanelEntityStyleTabBase.cs` | ~423 | 实体样式 Tab 基类：公共样式 UI/保存/加载 |
| `DebugPanelMapTab.cs` | ~1309 | 地图 Tab：网格/摄像机/校准/响应式/编辑器 |
| `DebugPanelPlayerTab.cs` | ~1624 | 玩家 Tab：外观/文字/标签/血条/施法条/动作栏/等级徽章 |
| `DebugPanelMonsterTab.cs` | ~521 | 怪物 Tab：全局样式/标签/AI/血条/MP条 |
| `DebugPanelNpcTab.cs` | ~150 | NPC Tab：全局样式/标签/交互菜单偏移 |
| `DebugPanelSystemTab.cs` | ~132 | 系统 Tab：移动系统配置 |
| `DebugPanelUITab.cs` | ~365 | UI Tab：技能栏/功能按钮栏配置 |

### 配置文件

- 主配置：`user://debug_panel_config.cfg`（ConfigFile 格式）
- 预设文件：`user://debug_panel_presets.cfg`
- 当前版本：`CONFIG_VERSION = 2`

## 2. Bug 与问题

### 🔴 P0 — 数据丢失

#### 2.1 PlayerTab 未保存边框/背景/文字颜色 ✅ 已修复

**位置**：`DebugPanelPlayerTab.cs` SaveConfig (L1309)

PlayerTab 手动写每个配置字段，**漏掉了 `BorderColor`、`BgColor`、`TextColor`** 的保存。MonsterTab/NpcTab 通过 `SaveCommonStyleConfig` 保存了这些字段，但 PlayerTab 没有。

- 修改玩家边框/背景/文字颜色 → 重启后丢失
- LoadConfig 也没有读取这些颜色

**修复**：在 PlayerTab.SaveConfig 中补充颜色保存，或在 PlayerTab 中也使用 `SaveCommonStyleConfig`。

#### 2.2 怪物样式保存后重启不生效（Bug #006）

**位置**：`DebugPanelMonsterTab.cs` + `MonsterManager.cs`

配置文件 `monster_1` 里有完整数据（包括 `hp_bar_length_scale=1.183`），保存/加载 key 名匹配，MonsterId 映射正确。但陛下反馈修改后重启丢失。

**已排查**：保存/加载链路代码逻辑正确，无法通过日志验证（Godot DLL 缓存问题）。

**待确认**：需要陛下确认具体操作步骤和现象。

### 🟡 P1 — 功能缺陷

#### 2.3 MonsterId=3（野狼）没有 StyleConfig ~~✅ 已修复~~

**位置**：`MonsterManager.cs` GetStyleConfig (L23)

配置文件里只有 `monster_1` 和 `monster_2`，但 Luban 配置表有 3 种怪物（MonsterId=1/2/3）。`GetStyleConfig(3)` 回退到 `StyleConfigs.Values.First()`，字典遍历顺序不确定。

- 野狼的样式配置无法独立管理
- 调试面板里没有配置 ID 3 的选项

**修复**：`SpawnMonsters` 时自动为每个 MonsterId 创建 StyleConfig（从已有配置复制）。✅ 已修复

#### 2.4 EntityBase 缺少 HealthBarCenterX / MpBarCenterX 属性 ~~✅ 已修复~~

**位置**：`EntityBase.cs` ApplyStyle (L238)

`EntityStyleConfig` 里有 `HpBarCenterX`/`MpBarCenterX`，`SaveBarConfig` 保存了 `hp_bar_center_x`，`LoadStyleConfigFromSection` 读取了它。但 `EntityBase.ApplyStyle` 没有设置 `HealthBarCenterX`——因为 EntityBase 根本没有这个属性。

- 居中状态只能通过 `HpBarOffsetX == 0` 推断
- `SyncFromEntity` 里用 `entity.HealthBarOffset.X == 0` 推断居中状态，不精确

**修复**：在 EntityBase 中添加 `HealthBarCenterX`/`MpBarCenterX` 属性，并在 `ApplyStyle` 中设置。✅ 已修复

#### 2.5 撤销系统已禁用但代码残留 ✅ 已修复

**位置**：`DebugPanel.Undo.cs` + 各 Tab 的 `CaptureUndoState`/`ApplyUndoState`

`PushCurrentStateToHistory()` 是 no-op，但各 Tab 仍实现了 `CaptureUndoState`/`ApplyUndoState`（MapTab 有完整实现，PlayerTab 有空实现，EntityStyleTabBase 有空实现）。

- 用户可能误以为撤销功能可用
- MapTab 的 Undo 实现永远不会被调用

**修复**：要么重新实现撤销系统，要么删除所有 Undo 相关代码。

#### 2.6 PlayerTab 同时保存 player_size 和 visual_size_scale ✅ 已修复

**位置**：`DebugPanelPlayerTab.cs` SaveConfig (L1312-1313)

重构后 Scale 是唯一真相源（`VisualSize = GridSize × VisualSizeScale`），但 PlayerTab 仍保存 `player_size`（绝对值）和 `visual_size_scale`。LoadConfig 也读取两者。

- `player_size` 是冗余数据，可能与 Scale 计算结果不一致
- 加载时如果 `player_size` 和 `visual_size_scale` 冲突，行为不确定

**修复**：移除 `player_size` 的保存/加载，只保留 `visual_size_scale`。

### 🟢 P2 — 代码质量

#### 2.7 预设保存的 fixedSections 列表硬编码 ✅ 已修复

**位置**：`DebugPanel.cs` DeferredInit (L158-165)

**位置**：`MonsterManager.cs` (L20), `NpcManager.cs` (L56)

#### 2.10 配置迁移只处理了 monster → monster_1

**位置**：`DebugPanel.Config.cs` MigrateConfig (L447)

v1 → v2 迁移只处理了 `[monster]` → `[monster_1]` 和 `[npc]` → `[npc_1]`。如果未来有更多迁移需求，需要扩展。

## 4. 架构问题

### 4.1 PlayerTab 未使用 EntityStyleTabBase

PlayerTab 是独立实现（1624 行），没有继承 `DebugPanelEntityStyleTabBase`。这导致：
- 公共样式逻辑重复（颜色保存缺失就是因此引入的）
- 无法复用 `SaveCommonStyleConfig`/`SaveBarConfig`
- 代码量远超其他 Tab

**建议**：将 PlayerTab 重构为继承 EntityStyleTabBase，与 MonsterTab/NpcTab 统一。

### 4.2 配置保存是全量覆盖

`SaveConfig()` 每次创建新的空 ConfigFile，写入所有 tab 的数据，然后覆盖保存。这意味着：
- 任何不在 tab SaveConfig 里的数据都会丢失
- 如果某个 tab 的 SaveConfig 有 bug（如 PlayerTab 漏了颜色），对应数据就永久丢失

### 4.3 MonsterManager/NpcManager 直接读取 DebugPanel 的配置文件

`MonsterManager._Ready` → `LoadDefaultStyleConfig` → 读取 `user://debug_panel_config.cfg`。这创建了 DebugPanel 和 Manager 之间的隐式耦合。

- 如果 DebugPanel 改了配置文件格式，Manager 也受影响
- Manager 在 DebugPanel 之前初始化，依赖配置文件已存在
