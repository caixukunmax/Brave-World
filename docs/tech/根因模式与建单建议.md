## P0：服务端权威缺失（模式6）

### 建单 1：无限回血修复（PlayerSnapshot 残留问题）
- **现状**：EnterGameHandler/ChangeMapHandler 内存 Role 对象已不强制覆盖为满血（部分修复）
- **残留问题**：EnterGameHandler 第97行 `Hp = hp, MaxHp = hp`（PlayerSnapshot 用满血值），MapPlayerState 看到的是满血玩家
- **修复方案**：改为 `Hp = role.Hp, MaxHp = hp, Mp = role.Mp, MaxMp = mp`
- **风险**：中 — 改动小，但需确认 role.Hp 在 EnterGame 时一定是有效值
- **验证**：服务端测试 + 登录后检查 MapPlayerState.Hp != MaxHp

### 建单 2：掉落系统集成
- **现状**：DropManager.cs 存在但无调用方，DeathResponder 不调用 GenerateDrops
- **修复方案**：在 DeathResponder 中调用 DropManager.GenerateDrops + 注册到 GameLogicFactory + 实现 PickupDropRequest 协议处理器
- **风险**：中 — 新功能集成，需双端联调
- **验证**：怪物死亡后地图上出现掉落物 + 玩家可拾取

### 建单 3：怪物 Buff 属性修正实现
- **现状**：DealDamageAction.GetBuffAttrModifier 怪物分支 return 0
- **修复方案**：从 CombatContext 的 BuffContainer 获取属性修正值（与玩家分支逻辑一致）
- **风险**：低 — 逻辑已有玩家分支参考，怪物分支只需复制
- **验证**：给怪物施加破甲 debuff 后伤害增加

## P1：非原子操作 + 信号泄漏（模式3+4）

### 建单 4：InventoryRepository 原子化
- **现状**：AddItem/RemoveItem 用 Find+Update 两步操作，并发时数量错误
- **修复方案**：
  - AddItem：改用 `FindOneAndUpdateAsync` + `$inc` 操作符 + `IsUpsert = true`
  - RemoveItem：改用 `FindOneAndUpdateAsync` + 条件更新（`Gte(count)` + `$inc(-count)`），结果 <=0 则删除
- **风险**：中 — 核心数据操作，需充分测试并发场景
- **验证**：并发 AddItem/RemoveItem 测试

### 建单 5：AutoSave 补全字段
- **现状**：AutoSave 不保存 Gold/Diamond/TotalPower/VipLevel 等经济数据
- **修复方案**：在 AutoSave 中补全所有 Role 字段，或改用全量 Update
- **风险**：低 — 当前无代码修改这些字段，预防性修复
- **验证**：修改 Gold 后等 5 分钟自动保存，重启后 Gold 值一致

### 建单 6：NpcManager 信号泄漏修复
- **现状**：_ExitTree 只取消 NpcInteractNotify（1/4），漏掉 NpcCombatResponse/CombatStateNotify/CombatEndNotify
- **修复方案**：在 _ExitTree 中补全 3 个信号取消
- **风险**：低 — 改动极小（3行代码）
- **验证**：场景切换后不再收到战斗通知

### 建单 7：PlayerSessionManager 下线清理
- **现状**：只有 SetOnline 没有 SetOffline，断线后 _onlinePlayers 字典只增不减
- **修复方案**：添加 SetOffline 方法 + 在 GatewayService.CloseConnection 中调用 + 清理 MapService 中的玩家实体
- **风险**：中 — 涉及断线流程，需测试断线重连
- **验证**：断线后 _onlinePlayers 不再包含该玩家 + 重连后状态正确

## P2：async void 反模式（模式1）

### 建单 8：async void 统一修复
- **现状**：客户端 11 处 async void，服务端 0 处
- **统一修复方案**：
  ```csharp
  public static async void SafeRun(Func<Task> taskFactory, [CallerMemberName] string caller = "")
  {
      try { await taskFactory(); }
      catch (Exception ex) { GD.PrintErr($"[{caller}] Async error: {ex}"); }
  }
  ```
- **修复优先级**：
  1. 🔴 NetworkManager.ConnectToServer — 网络操作最不可靠，必须优先修
  2. 🟡 Player.Labels — 已有 Task 内部方法，改动最小
  3. 🟡 CameraController/MapManager/MapEditor _Ready — 统一模式
  4. 🟡 ScreenshotTool.TakeScreenshot — 文件操作
  5. 🟢 其余4处 — 低风险，可后续批量处理
- **风险**：低 — 统一模式，改动明确
- **验证**：NetworkManager 连接异常时不再崩溃 + 其他 _Ready 异常时打印错误而非崩溃

## P3：硬编码配置（模式2）

### 建单 9：NPC 配置表 + NpcType Protobuf 生成
- **现状**：NpcType 枚举双端手动维护，NPC 战斗属性硬编码，NPC 列表硬编码
- **修复方案**：
  1. 创建 common_tbnpc.xlsx 配置表（NpcId/Name/MapName/X/Y/NpcType/CombatAttrs）
  2. NpcType 迁移到 Protobuf enum → 自动双端同步
  3. NpcManager.Init() 从配置表加载 NPC 列表
  4. NpcCombatHandler 从配置表读取战斗属性
- **风险**：中 — 涉及双端同步和配置表创建
- **验证**：新增 NPC 类型只需改 proto + 配置表，不需改代码

### 建单 10：客户端硬编码清理
- **现状**：ChangeJobPanel 职业列表硬编码3个，EquipSkillHandler 硬编码4槽位，InitItems 硬编码字符串
- **修复方案**：
  1. ChangeJobPanel 从服务端推送或 Luban 配置读取职业列表
  2. EquipSkillHandler 槽位数从 GameConstants 读取
  3. InitItems 迁移到 Luban 配置表
- **风险**：低 — 低频改动，不影响核心功能
- **验证**：新增职业/修改槽位数只需改配置

## P4：双系统并存清理（模式5）

### 建单 11：EntityStyleConfig 旧系统清理
- **现状**：旧系统仍被调用但结果被 ApplyProfile 覆盖，约 15 个方法是死代码
- **修复路线图**：
  1. 删除死代码（ApplyStyleToAll, SetXxxAll×12, SyncStyleConfigFromEntity）
  2. 移除 ApplyDefaultStyle 调用（被 ApplyProfile 覆盖，冗余）
  3. 将 EntityStyleConfig 标记为 [Obsolete] 或移到 Legacy 命名空间
  4. Player 标签遮蔽：长期方案是统一 Player 和 EntityBase 的标签系统
  5. Legacy.cs 在所有配置迁移完成后删除
- **风险**：低 — 删除死代码和冗余调用，不影响功能
- **验证**：删除后游戏行为不变（ApplyProfile 仍正确覆盖）
