# AI 每轮提交分支工作流设计

## 概述

为 AI 辅助开发建立一个 Project 级 skill：AI 在每次回答并产生代码/配置/文档改动后，自动提交到固定的 `ai/working` 分支，并在提交信息中记录用户提问、AI 理解和问题背景。出现问题时，可通过 git 提交历史快速定位是哪一轮修改引入了 bug。

## 目标

1. **可追溯**：每一轮用户请求与对应的代码改动一一对应。
2. **可回滚**：发现 bug 时，能精确回滚到某一轮之前的状态，而不必一次性丢弃整个会话的工作。
3. **可复盘**：通过提交信息中的上下文字段，事后能理解当时为什么那样改。
4. **轻量**：不引入额外的 session-log 文件，所有信息写入 git commit message。

## 分支模型

- **固定分支名**：`ai/working`
- **基线策略**：会话开始时若分支不存在，从当前分支（通常为 `master`）创建；若已存在，保留现状继续提交。
- **不自动合并**：AI 只维护 `ai/working`，最终是否合并、何时合并由用户决定。
- **不自动 push**：提交仅存在于本地，避免污染远程历史。

## Turn 编号

- Turn 编号跨会话连续递增，不重置。
- 新 turn 编号 = `ai/working` 分支上已有的最大 turn 编号 + 1。
- 通过 `git log --grep="\[turn-" --oneline ai/working` 解析最新编号。
- 续接/补充时沿用同一编号，不递增。

## 提交信息格式

每次产生文件改动后，使用统一模板提交：

```
[turn-003] 修复 GridShaderOverlay 的 return 问题

【用户提问】
地图渲染还是灰色，之前改完后没有网格。

【AI理解】
shader 中使用了未定义的 return，导致 fragment 行为异常。

【问题背景】
本次调试是为了验证 GridShaderOverlay 是否真正被绘制；已确认是被绘制，问题在 shader 逻辑本身。

【动作】
- 恢复 grid_overlay.gdshader 真实渲染逻辑
- 移除 fragment 中未定义的 return
- GridShaderOverlay.cs 绘制地图尺寸 rect

【验证】
dotnet build clinetcsharp/clinetcsharp.csproj 通过
```

### 字段规则

| 字段 | 必填 | 说明 |
|------|------|------|
| `[turn-NNN] <一句话标题>` | 是 | 统一前缀，便于 grep 与排序 |
| 【用户提问】 | 是 | 用户原话或核心意图摘要 |
| 【AI理解】 | 是 | AI 对问题/需求的判断 |
| 【问题背景】 | 可选 | 存在前置上下文或调试链路时填写 |
| 【动作】 | 是 | 修改了哪些文件、关键决策 |
| 【验证】 | 是 | 运行了什么验证命令及结果；无则写"未验证" |

## 工作流程

### 正常开发轮次

1. 用户提问。
2. AI 思考并产生修改。
3. 修改完成后：
   - `git status --short` 检查是否有改动。
   - 有改动则按模板生成提交信息并提交到 `ai/working`。
   - 无改动则不提交。

### 回溯 bug

1. 用户报告"某处坏了"。
2. AI 查看 `git log --oneline ai/working -n 20` 列出最近轮次。
3. 确定一个好提交和一个坏提交：
   - 好提交：用户确认当时正常的最近提交。
   - 坏提交：当前 `ai/working` HEAD 或已知出问题的提交。
4. 运行 `git bisect`：
   - 若项目有自动验证命令（如 `npm run verify`、`dotnet test`），使用 `git bisect run <cmd>`。
   - 否则采用手动二分，每步让 AI 检查状态。
5. 定位到 `[turn-XXX]` 后：
   - `git show <commit>` 查看该轮上下文、改动和验证结果。
   - 分析根因并给出修复建议。

## 与项目现有规则的集成

- 仍然遵守 `AGENTS.md` 的"文档先行"原则：有文档冲突时先更新文档再改代码。
- 仍然遵守 Bug 修复框架：修复前先溯源、治本、免疫。
- 每轮提交前，优先运行项目快速验证命令（如 `dotnet build`）。
- 不替代用户最终的 `git commit/push` 决策，仅作为 AI 的工作记录。

## 续接与补充的处理

以下用户输入视为对上一轮任务的延续，**不新建 turn 编号**：

- "继续"
- "continue"
- "接着说"
- "刚才没处理完"
- "补充一下"
- 对上一轮同一话题的追问或补充说明

### 提交策略

1. **首次有效改动**：分配 `[turn-NNN]`，正常提交。
2. **续接时又有新改动**：
   - 若上一轮任务已完整完成，则开启新 turn。
   - 若上一轮因中断未完成，则沿用同一 turn 编号，提交标题加 `（补充）` 后缀。
3. **用户明确切换话题**：分配新的 turn 编号。

### 任务完成判定

AI 在每次修改后自评：

- **完成**：改动解决了用户本次提出的完整问题，下一轮新话题时开启新 turn。
- **未完成**：改动只是中间步骤，或用户明确说"继续"，沿用当前 turn。

续接提交的示例：

```
[turn-003] 修复 GridShaderOverlay 的 return 问题（补充）

【用户提问】
（续接）继续处理地图渲染问题。

【AI理解】
上一轮 shader 已恢复，但 Background 颜色仍为透明，需要补回黑色。

【动作】
- 恢复 Background ColorRect 颜色为黑色

【验证】
游戏运行后背景为黑色
```

## 边界情况

| 场景 | 处理 |
|------|------|
| 本轮无文件改动 | 不提交，不记录 |
| 用户明确说"不要提交" | 跳过提交 |
| 验证失败 | 仍提交实际状态，验证字段写"失败：..." |
| `ai/working` 与 `master` 偏离很远 | 不自动 rebase/merge，仅提醒用户 |
| 单轮内多个独立子任务 | 合并为一个提交，动作列表分点列出 |
