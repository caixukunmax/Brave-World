# 客户端 UI 面板架构整理

> 状态：已实现
> 日期：2026-05-09
> 范围：`clinetcsharp/` 客户端通用 UI 面板体系

## 1. 背景

当前客户端已经有一套可复用的通用面板底座：

- `DraggablePanel`：负责拖拽、缩放、最小化、关闭、焦点、快捷键
- `PanelManager`：负责注册、置顶、焦点切换、按键切换

但业务面板的实现方式并不统一：

- `IntegratedPanel`、`InventoryUI` 更接近“场景骨架 + 脚本填充内容”
- `SkillPanel` 仍然在 `_Ready()` 里动态创建整棵场景树
- `GMPanel`、`CharacterPanel` 仍然把 UI 结构、业务逻辑、服务发现写在同一个文件里

这会带来三个持续性问题：

1. 面板结构难以在编辑器中直接调整和预览
2. 业务脚本同时承担布局和交互，职责边界模糊
3. 多个面板直接依赖硬编码路径，后续场景调整风险高

## 2. 本轮目标

本轮不推翻现有 UI，而是把通用约定明确下来，并落地一个示范重构。

目标：

1. 统一面板实现模式为“场景骨架 + 业务脚本”
2. 统一通用依赖获取方式，减少 `/root/...` 和场景路径硬编码
3. 选 `SkillPanel` 作为第一批重构对象

## 3. 统一约定

### 3.1 面板骨架

业务面板统一继承 `DraggablePanel`，场景结构统一为：

```text
PanelRoot (PanelContainer, script=业务面板)
└─ VBoxContainer
   ├─ TitleBar
   │  └─ HBoxContainer
   │     ├─ MinimizeButton
   │     ├─ TabLabel / TitleLabel
   │     ├─ Spacer
   │     └─ CloseButton
   └─ Content
      └─ 业务内容节点
```

约束：

- 标题栏、最小化、关闭都交给 `DraggablePanel`
- 顶层壳子必须尽量静态化到 `.tscn`
- 脚本只负责业务内容刷新、事件订阅、交互处理

### 3.2 依赖获取

面板脚本不再直接散落硬编码路径。

统一通过轻量助手类获取常用服务：

- `UiServices.GetNetworkManager(Node)`
- `UiServices.GetInventoryManager(Node)`

这样做的目的不是引入复杂 IOC，而是先把最脆弱的路径依赖收口到一个地方，后面如果主场景结构变化，只需要改一处。

### 3.3 面板脚本职责

面板脚本只保留三类职责：

1. 发现业务节点引用
2. 订阅和释放业务事件
3. 根据缓存数据刷新 UI

不再承担：

1. 整体场景树拼装
2. 通用面板行为实现
3. 到处复制的服务定位逻辑

## 4. 首批改造对象

### 4.1 SkillPanel

`SkillPanel` 是当前最适合示范性重构的对象：

- 已经继承 `DraggablePanel`
- 业务职责清晰
- 但仍然在代码中创建完整标题栏、列布局、详情区

本轮改造：

1. 将 `SkillPanel` 改为静态 `.tscn` 骨架
2. 脚本只保留节点发现、刷新逻辑和操作回调
3. 接入 `UiServices`，去掉对 `/root/NetworkManager` 的直接依赖

### 4.2 GMPanel

`GMPanel` 是第二个高价值对象：

- 当前主文件同时承载数据模型、默认命令、内联编辑、右键菜单、命令执行、响应处理
- 场景壳子已经统一，但内容层职责仍然过于集中

本轮改造：

1. 主文件只保留生命周期、节点引用和依赖订阅
2. `Data` 部分负责分组模型和默认命令
3. `Build` 部分负责内容构建、内联编辑和列表重建
4. `Actions` 部分负责命令发送、响应处理和日志

这样做的目标不是一次性改成复杂架构，而是先把 `GMPanel` 从“单文件脚本块”收敛成可继续演进的模块。

### 4.3 CharacterPanel

`CharacterPanel` 虽然体量不大，但它是一个很典型的“轻业务面板”：

- 数据定义简单
- UI 由重复属性行组成
- 交互主要是刷新和批量发送命令

本轮改造：

1. 主文件只保留生命周期和面板订阅逻辑
2. `Data` 部分负责属性定义和控件映射
3. `Build` 部分负责动态属性行和底部操作区构建
4. `Actions` 部分负责刷新与 GM 命令发送

它会作为后续类似面板的最小模板。

### 4.4 InventoryUI

`InventoryUI` 是典型的“列表/网格型面板”：

- 面板骨架已经统一
- 内容区是纯动态生成
- 交互聚焦在刷新格子和弹出操作菜单

本轮改造：

1. 主文件只保留生命周期和订阅逻辑
2. `Build` 部分负责内容区和格子按钮构建
3. `Actions` 部分负责刷新、空槽补齐和物品操作菜单

它会作为后续背包、列表、卡片类面板的参考模板。

### 4.5 DebugPanelUITab

`DebugPanel` 体系里，`DebugPanelUITab` 是最适合作为下一步切入口的 tab：

- 逻辑边界清楚，只负责 UI 相关调试项
- 没有地图编辑、实体配置那种强耦合状态
- 但当前仍把构建、信号、应用逻辑、配置读写堆在一个文件里

本轮改造：

1. 主文件只保留字段、构造和 `TabKey`
2. `Build` 部分负责 UI 搭建
3. `Signals` 部分负责连接、应用和按钮回调
4. `Config` 部分负责配置保存、加载、同步

这样可以把 `DebugPanel` tab 层也拉到和业务面板一致的组织方式。

### 4.6 DebugPanel 主文件

在 tab 层开始拆分后，`DebugPanel.cs` 本身也需要继续瘦身：

- 当前仍同时承载生命周期、延迟初始化、跨 tab 状态同步、面板显示状态、标签切换、实体点击跳转
- 这些逻辑虽然都属于“面板级”，但已经不适合继续堆在同一个主文件

本轮改造：

1. 主文件只保留常量、字段和少量通用入口
2. `Lifecycle` 部分负责 `_Ready / _ExitTree / _Input / _Process / DeferredInit`
3. `PanelState` 部分负责标签显隐、面板可见性同步、实体点击切 tab

这样 `DebugPanel` 自身也会和其他 UI 模块一样，进入“主文件只做总线，细节逻辑分仓”的状态。

### 4.7 DebugPanelMapTab

`DebugPanelMapTab` 仍然是当前 UI 层最重的单块之一：

- 已经拆出 `Build`
- 但信号连接、地图/相机事件处理、配置读写、同步状态仍然堆在主文件

本轮改造：

1. 主文件保留字段、公开访问器和事件处理函数
2. `Signals` 部分负责 `ConnectSignals / DisconnectSignals`
3. `Config` 部分负责保存、加载、导出和初始应用
4. `Sync` 部分负责当前值同步、相机缩放同步和控件可编辑状态

这样 `MapTab` 也能进入和 `UITab` 一样的组织方式，后面再拆 `EntityTab` 会顺很多。

### 4.8 DebugPanelEntityTab

`DebugPanelEntityTab` 是 `DebugPanel` 体系里第二个高复杂度模块：

- 同时负责 Profile 列表、组件增删启停、运行期同步、配置持久化、撤销快照
- 业务逻辑不在 UI 表面，而在组件化数据流里

本轮改造：

1. 主文件只保留字段、构造和 `TabKey`
2. `Build` 部分负责 UI 和对话框搭建
3. `Profile` 部分负责 Profile 选择、创建、删除、重命名
4. `Components` 部分负责组件管理、刷新和实体点击同步
5. `Config` 部分负责保存、加载、撤销和导出

这样 `EntityTab` 的结构会和 `MapTab` 一样清晰，`DebugPanel` 体系基本就进入可持续维护状态了。

### 4.9 DebugPanelSystemTab

`DebugPanelSystemTab` 虽然逻辑轻，但它是 `DebugPanel` 体系里最后一个标准 tab：

- 负责全局系统参数展示与同步
- 没有复杂交互，但仍然需要和其他 tab 保持相同组织方式

本轮改造：

1. 主文件只保留字段、构造和 `TabKey`
2. `Build` 部分负责 UI 搭建
3. `Config` 部分负责 `Save / Load / Sync`

这样 `DebugPanel` 体系四个主要 tab 的组织方式就统一了。

### 4.10 后续建议顺序

后续继续按这个顺序推进：

1. `GMPanel`：继续从动态内容构建过渡到更多静态场景节点
2. `CharacterPanel`：如需继续演进，可把底部按钮区也静态化到场景
3. `InventoryUI`：如需继续演进，可把格子渲染抽到单独控件或场景

## 5. 非目标

本轮明确不做：

1. 不全面重做所有面板视觉样式
2. 不把所有动态列表都改成纯静态场景
3. 不引入完整 MVVM / 数据绑定框架
4. 不修改 `DraggablePanel` 的核心交互语义

## 6. 验证方式

至少验证：

1. `SkillPanel` 可正常打开、关闭、最小化、拖拽、缩放
2. 技能装备、卸下、学习、详情查看功能保持不变
3. `InventoryUI`、`CharacterPanel`、`IntegratedPanel`、`GMPanel` 在依赖收口后仍能正常编译
## 7. 第二层优化

在 `DebugPanel` 的主文件和四个主要 tab 都完成拆分后，下一步优化重点不是再拆更多文件，而是把重复最多的 UI 模板代码收口到 `DebugPanelTab` 基类。

本轮改造：

1. 在 `DebugPanelTab` 中新增 tab 标题和分隔线等通用布局助手。
2. 让 `DebugPanelMapTab`、`DebugPanelUITab`、`DebugPanelEntityTab`、`DebugPanelSystemTab` 的 `Build` 代码改用这些公共助手。

这样做的价值是后续继续扩展调试 tab 时，不需要每次都手写一遍“标题 + 分隔线”的样板代码，维护成本会继续下降。
## 8. DebugPanel 纠偏

在完成 `DebugPanel` 主体与各 tab 的结构拆分后，又补了一轮交互层纠偏，目标不是继续切文件，而是清掉几处“职责边界已经分开，但行为语义还混着”的问题：

1. `Preset` 保存改为基于当前内存态快照，而不是重新读取磁盘上的旧 config
2. `EntityTab` 只在 `DebugPanel` 可见时响应全局 `EntityClicked`
3. “面板字段标签”与“实体头顶标签”拆成两个独立开关，不再共用一个按钮
4. 已停用的 `Undo` 调用链清理掉，避免继续给维护者制造错误预期

同时，`EntityTab` 的组件启停、增删和 profile 变更也补上了延迟保存，避免出现“界面里看起来改了，但配置文件没落盘”的状态漂移。

## 9. DebugPanel Config 收口

在完成上一轮交互纠偏后，`DebugPanel` 的配置层又继续做了一次结构收口：

1. 正式保存与预设保存统一复用同一个 `BuildCurrentConfigSnapshot()` 入口
2. `DebugPanel.Config.cs` 不再继续堆叠所有职责，而是拆成：
`DebugPanel.Config.Persistence.cs`
`DebugPanel.Config.Presets.cs`
`DebugPanel.Config.Migration.cs`
`DebugPanel.Config.Export.cs`
3. `panel_ui` 相关状态与 tab 配置、面板几何一起进入同一条持久化路径

这样后面再改 preset、save/load、migration 或 export 时，就不会再出现“改了一处、漏了另一处”的分叉行为。

## 14. MapTab 分组再整理

`MapTab` 第二轮整理不再只关注“方案切换时隐藏无关参数”，还要把剩余杂项按职责归位，避免“策略参数、镜头控制、调试开关、编辑器输入”混在同一长列里。

这一轮的结构约定如下：

1. `格子方案`
   包含 `方案`、对应参数，以及 `视角远近`。原因是手动格子大小时，视角远近会直接改变屏幕可见格子数；响应式格子大小时，视角又会进入自动受控状态，所以它属于格子可见尺度的一部分，而不是普通杂项。
2. `线宽方案`
   只包含线宽策略、对应参数和线条亮度，不再混入镜头行为。
3. `镜头行为`
   包含 `自由视角`、`恢复延迟`、`回退速度`、`缓动曲线`、`缓动强度`，专门描述镜头脱离/回归玩家时的体验。
4. `调试显示`
   包含 `显示格子坐标`、`显示调试信息`、`相机拖拽调试输出` 这类纯显示/日志开关。
5. `编辑输入`
   包含 `拖动视野按键`、`Ctrl+点击选中` 这类地图编辑模式输入约定。

这样整理后，用户在 `MapTab` 中会先决定“格子怎么显示”，再决定“线怎么画”，然后才处理“镜头怎么动”和“调试怎么开”，认知顺序更稳定。

## 15. MapTab 怪物巡逻区域总览

`MapTab` 的“调试显示”分组新增一个轻量开关：

1. `显示所有怪物巡逻区域`

目标：

1. 一键浏览当前地图所有怪物的巡逻范围
2. 只做调试可视化，不影响怪物运行逻辑
3. 不把怪物表读取、范围绘制硬塞回 `GridManager`

实现约定：

1. `MapTab` 只负责开关、配置保存和同步
2. 新增独立 overlay 节点挂在地图层，专门绘制巡逻区域
3. overlay 优先读取生成表：
   - `servercsharp/data/tables/common_tbai.json`
   - `servercsharp/data/tables/common_tbmapmonster.json`
   - `servercsharp/data/tables/common_tbmapconfig.json`
4. 若生成表不可用，再回退到客户端 `monster_config.json`

可视化规则：

1. 只显示当前地图的怪物刷怪点
2. 以出生格为中心，按 `patrol_range` 画出巡逻边界
3. `patrol_range <= 0` 时不画区域
4. 区域样式保持半透明、细线、不可交互，避免压过主网格

这样后面继续扩 `显示仇恨范围 / 显示施法距离 / 显示最大追击距离` 时，也能沿用同一套 overlay 结构，而不是继续膨胀 `GridManager` 或 `MapTab`。
## 15. EntityTab 与标签开关整理

`DebugPanel` 这一轮对 `EntityTab` 做两件事：

1. 把“玩家/怪物/NPC 共用的实体配置页”整理成更清楚的几块：
   `当前配置`、`配置操作`、`组件管理`、`当前组件`。
   这样用户虽然仍在 `EntityTab` 中编辑玩家 profile，但扫描路径更像一个稳定的“玩家/实体配置页”，而不是一串散控件。
2. 移除 `隐藏面板标签` 和 `隐藏实体标签` 两个全局按钮，以及它们的持久化状态。
   原因是这两个开关既不是高频调参项，也会和实体真实标签观察需求冲突；移除后 `DebugPanel` 保持默认可见状态，不再引入额外全局 UI 状态。

新的约定：

1. `EntityTab` 顶部先展示当前 profile 选择和名称编辑。
2. 新建/删除 profile 单独成块，不和 profile 下拉混排。
3. 组件管理入口单独成块，并给出简短说明。
4. 当前组件列表独立成块，和“管理组件”弹窗形成主从关系。
5. `DebugPanel` 不再保存 `panel_ui.show_panel_labels/show_entity_labels`。
## 16. 标签字体配置整理

`labels` 组件这一轮从“隐式兜底 + 部分空壳控件”收成显式模型。

目标约定：

1. 保留一份清晰的全局标签字体配置：
   `默认字号`、`粗体`、`斜体`、`阴影`。
2. 每个小标签都可以单独设置字号，但通过显式开关控制：
   `使用全局字号`。
3. 当某个标签勾选 `使用全局字号` 时：
   它的局部字号控件只作为参考值保留，不参与实际渲染，真正渲染时回退到全局默认字号。
4. 移除没有真正打通渲染链路、或职责重复的入口：
   `字体下拉 / 加载按钮`、
   `默认颜色 / 单标签颜色按钮`。
   原因是当前实体标签颜色已经由外观层 `TextColor` 统一负责，这些控件只会制造“UI 有、实际不稳定生效”的错觉。
5. 序列化层对旧配置保持兼容：
   旧配置如果没有显式 `use_global_font`，则按 `font_size <= 0` 解释为跟随全局。

落地后，`labels` 组件的语义会变成：
“全局样式负责共性，每个标签只在必要时脱离全局做局部字号覆盖”，避免继续依赖 `0` 这种隐式语义。
