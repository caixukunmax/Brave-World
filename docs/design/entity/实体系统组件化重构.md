> 状态：设计中

> 决策来源：`../../daily/2026-05/2026-05-04.md` 架构讨论

---

## 1. 架构决策回顾

### 核心原则
- **服务端决定"是什么"**（EntityType + 组件列表）
- **客户端决定"怎么画"**（按渲染方式分继承）
- **组件化 > 继承**：能力按组件组合，不靠继承链

### 服务端：组件化驱动
```
ServerEntity + 能力组件（Combat/Move/Cast/AI/Interact/Gather）
按实体类型配置组件组合：
  Player     → {Combat, Move, Cast}
  Monster    → {Combat, Move, AI, Cast}
  Npc        → {Combat, Interact}
  GatherNode → {Combat, Gather}
```

### 客户端：按渲染类型继承
```
EntityBase + 渲染组件（只管 UI/动画）
Monster/Npc/Boss 按渲染方式分继承
前端组件只管"怎么画"，不做逻辑计算
```

### 协议
```
EntityType + 组件列表，服务端告诉客户端实体信息
```

## 2. 现状分析

### 2.1 服务端现状

| 文件 | 说明 |
|---|---|
| `WorldDataTypes.cs` | `CombatEntityState`（属性字典）+ `MapPlayerState`/`MapMonsterState`/`MapNpcState`（继承它） |
| `MonsterRuntimeState.cs` | 怪物完整状态：位置、AI、移动、战斗属性（与 MapMonsterState 重复） |
| `MonsterManager.cs` | 怪物 AI tick、移动、战斗 |
| `NpcManager.cs` | NPC 初始化、查询 |
| `NpcCombatHandler.cs` | NPC 战斗处理 |
| `WorldState.cs` | 地图状态：Players/Monsters/Npcs 三个字典 + 移动预占 |
| `EntityType.cs` | `MapEntityType` 枚举（Chest/Npc/Portal/Monster） |

**问题：**
1. `CombatEntityState` 已有属性字典，但 `MonsterRuntimeState` 又自己声明了 `Hp/MaxHp/Patk/Mdef` 等——**两套属性系统并存**
2. `MapMonsterState` 和 `MonsterRuntimeState` 职责重叠——一个存地图位置，一个存运行时状态
3. NPC 没有独立运行时状态，`MapNpcState` 兼当状态和位置
4. 没有统一的 EntityBase，Player/Monster/Npc 各自独立存储在 WorldState 的三个字典里
5. `WorldState.FindEntityPosition` / `GetEntityName` 靠遍历三个字典——没有统一实体索引

### 2.2 客户端现状

| 文件 | 行数 | 说明 |
|---|---|---|
| `EntityBase.cs` | ~300 | 基类：外观、血条、MP条、施法条、动作栏、标签、移动基础 |
| `Player.cs` | ~1200 | 玩家：RichTextLabel 标签、复杂移动（服务端校验）、等级徽章 |
| `Monster.cs` | ~150 | 怪物：简单移动、Setup |
| `Npc.cs` | ~64 | NPC：最简单，只有 Setup + 绘制 |

**Phase 1-2 已完成的改进：**
- CastBar/ActionBar 已下沉到 EntityBase
- HitTest/SetGridSize/MoveTo/RollbackTo/PlayBounceBack 已在 EntityBase
- Manager.ApplyDefaultStyle → entity.ApplyStyle(cfg)

**仍存在的问题：**
1. 客户端继承体系是平的（EntityBase → Player/Monster/Npc），没有按"渲染方式"分组
2. 没有客户端组件概念——所有属性平铺在 EntityBase 里（~300 行属性声明）
3. Player 的移动逻辑（服务端校验）和 Monster 的移动逻辑（简单）差异巨大，但都 override 基类

### 2.3 协议现状

`game.proto` 中实体相关消息分散在各处（MoveRequest/CombatStateNotify 等），没有统一的实体创建/同步消息。

## 3. 重构目标

### 3.1 服务端目标

1. **统一实体基类** — `ServerEntity`，所有实体共享 ID/类型/位置/组件列表
2. **能力组件化** — Combat/Move/Cast/AI/Interact/Gather 按需组合
3. **统一实体索引** — WorldState 用一个字典管理所有实体，不再分三个
4. **消除状态重复** — MonsterRuntimeState 合并进组件系统
5. **EntityType 扩展** — 支持未来 Boss/Pet/Guard/GatherNode 等类型

### 3.2 客户端目标

1. **渲染组件化** — EntityBase 只留核心（位置、GridSize、绘制调度），渲染逻辑拆成组件
2. **按渲染方式继承** — Monster/Npc/Boss 的区别是"怎么画"，不是"有什么能力"
3. **客户端不做逻辑** — 战斗/移动/状态由服务端驱动，客户端只管动画和 UI

### 3.3 协议目标

1. **统一实体消息** — 实体创建/销毁/属性同步走统一协议
2. **组件列表下发** — 服务端告诉客户端"这个实体有哪些组件"

```csharp
// 服务端实体基类
public class ServerEntity
{
    public long EntityId { get; }
    public EntityType Type { get; }
    public string MapName { get; set; }
    public int X { get; set; }
    public int Y { get; set; }

    private readonly Dictionary<Type, IEntityComponent> _components = new();

    public T? GetComponent<T>() where T : class, IEntityComponent
        => _components.GetValueOrDefault(typeof(T)) as T;

    public void AddComponent<T>(T component) where T : class, IEntityComponent
        => _components[typeof(T)] = component;

    public bool HasComponent<T>() where T : class, IEntityComponent
        => _components.ContainsKey(typeof(T));

    public IEnumerable<IEntityComponent> GetAllComponents() => _components.Values;

    // ========== 事件系统 ==========
    private readonly Dictionary<EntityEventType, List<IEntityComponent>> _eventSubscribers = new();

    public void FireEvent(EntityEvent evt)
    {
        if (!_eventSubscribers.TryGetValue(evt.Type, out var subscribers)) return;
        foreach (var comp in subscribers)
        {
            if (evt.Handled) break;
            comp.OnEvent(evt);
        }
    }

    internal void SubscribeEvent(EntityEventType eventType, IEntityComponent component)
    {
        if (!_eventSubscribers.TryGetValue(eventType, out var list))
        {
            list = new List<IEntityComponent>();
            _eventSubscribers[eventType] = list;
        }
        if (!list.Contains(component)) list.Add(component);
    }

    internal void UnsubscribeEvent(EntityEventType eventType, IEntityComponent component)
    {
        if (_eventSubscribers.TryGetValue(eventType, out var list))
            list.Remove(component);
    }
}

// 实体事件类型
public enum EntityEventType
{
    Damage,       // 受伤
    Death,        // 死亡
    Heal,         // 治疗
    MoveStart,    // 开始移动
    MoveComplete, // 移动完成
    CastStart,    // 开始施法
    CastComplete, // 施法完成
    CastCancel,   // 施法取消
    Aggro,        // 进入战斗
    Disengage,    // 脱战
    Interact,     // 被交互
    Gather,       // 被采集
}

// 实体事件
public class EntityEvent
{
    public EntityEventType Type { get; }
    public ServerEntity Source { get; }  // 事件触发者
    public ServerEntity Target { get; }  // 事件目标
    public Dictionary<string, object> Data { get; } = new();
    public bool Handled { get; set; } = false;  // 组件可标记已处理，后续组件跳过
}

// 组件接口
public interface IEntityComponent
{
    void OnAttach(ServerEntity entity);
    void OnDetach(ServerEntity entity);
    void OnEvent(EntityEvent evt);  // 响应实体事件
}

// 组件基类（可选，简化订阅逻辑）
public abstract class EntityComponentBase : IEntityComponent
{
    protected ServerEntity Owner { get; private set; }

    /// <summary>声明本组件关心的事件类型，OnAttach 时自动订阅</summary>
    protected virtual EntityEventType[] InterestedEvents => Array.Empty<EntityEventType>();

    public virtual void OnAttach(ServerEntity entity)
    {
        Owner = entity;
        foreach (var evtType in InterestedEvents)
            entity.SubscribeEvent(evtType, this);
    }

    public virtual void OnDetach(ServerEntity entity)
    {
        foreach (var evtType in InterestedEvents)
            entity.UnsubscribeEvent(evtType, this);
        Owner = null;
    }

    public abstract void OnEvent(EntityEvent evt);
}

// 使用示例：CombatComponent 只关心它需要的事件
public class CombatComponent : EntityComponentBase
{
    protected override EntityEventType[] InterestedEvents =>
        [EntityEventType.Damage, EntityEventType.Heal, EntityEventType.Death];

    public override void OnEvent(EntityEvent evt)
    {
        switch (evt.Type)
        {
            case EntityEventType.Damage: HandleDamage(evt); break;
            case EntityEventType.Heal: HandleHeal(evt); break;
            case EntityEventType.Death: HandleDeath(evt); break;
        }
    }
}

// 其他组件定义
public class MoveComponent : EntityComponentBase { ... }     // 移动速度 + 移动状态
public class AiComponent : EntityComponentBase { ... }       // AI 配置 + AI 状态
public class CastComponent : EntityComponentBase { ... }     // 施法状态
public class InteractComponent : EntityComponentBase { ... }  // 交互配置
public class GatherComponent : EntityComponentBase { ... }    // 采集配置
```

```csharp
// 客户端渲染组件接口
public interface IRenderComponent
{
    int DrawOrder { get; }  // 绘制顺序：小值先画（底层），大值后画（顶层）
    void OnAttach(EntityBase entity);
    void OnDetach(EntityBase entity);
    void Draw();  // 在 EntityBase._Draw 中调用
}

// DrawOrder 约定
// 0   = 外观（AppearanceComponent / DrawBody）
// 100 = 血条/MP条（HealthBarComponent, MpBarComponent）
// 200 = 施法条/动作栏（CastBarComponent, ActionBarComponent）
// 300 = 标签（LabelComponent, RichLabelComponent）
// 400 = 等级徽章（LevelBadgeComponent）

// EntityBase 瘦身后
public abstract partial class EntityBase : Node2D
{
    public int GridSize { get; set; }
    public Vector2I GridPos { get; }

    private readonly List<IRenderComponent> _renderComponents = new();

    public void AddRenderComponent(IRenderComponent component)
    {
        _renderComponents.Add(component);
        _renderComponents.Sort((a, b) => a.DrawOrder.CompareTo(b.DrawOrder));  // 按 DrawOrder 排序
        component.OnAttach(this);
    }

    public T? GetRenderComponent<T>() where T : class, IRenderComponent
        => _renderComponents.OfType<T>().FirstOrDefault();

    public override void _Draw()
    {
        // 所有渲染组件（含外观）统一按 DrawOrder 绘制
        foreach (var comp in _renderComponents)
            comp.Draw();
    }
}
```

**实体创建流程：**

渲染组件分两层添加：
1. **EntityType 驱动**（客户端本地决定）：根据实体类型添加该类型必有的渲染组件（如 Player 必有 RichLabelComponent + LevelBadgeComponent）
2. **协议组件列表驱动**（服务端下发）：根据组件列表添加能力对应的渲染组件（如 CombatComponent → 血条+MP条）

```csharp
public static EntityBase CreateFromSnapshot(EntitySnapshot snapshot)
{
    // 1. 按 EntityType 创建实体
    EntityBase entity = snapshot.EntityType switch
    {
        EntityType.Player => new Player(),
        EntityType.Monster => new Monster(),
        EntityType.Npc => new Npc(),
        EntityType.Boss => new Boss(),
        _ => new Monster(),  // fallback
    };

    // 2. 添加 EntityType 必有的渲染组件（客户端本地决定，不依赖服务端）
    AddDefaultRenderComponents(entity, snapshot.EntityType);

    // 3. 按服务端组件列表添加能力对应的渲染组件
    foreach (var compType in snapshot.Components)
    {
        switch (compType)
        {
            case ComponentType.Combat:
                entity.AddRenderComponent(new HealthBarComponent());
                entity.AddRenderComponent(new MpBarComponent());
                break;
            case ComponentType.Cast:
                entity.AddRenderComponent(new CastBarComponent());
                entity.AddRenderComponent(new ActionBarComponent());
                break;
            case ComponentType.Interact:
                // NPC 交互提示等
                break;
        }
    }

    return entity;
}

private static void AddDefaultRenderComponents(EntityBase entity, EntityType type)
{
    // 所有实体都有外观
    entity.AddRenderComponent(new AppearanceComponent());

    // 类型特有
    switch (type)
    {
        case EntityType.Player:
            entity.AddRenderComponent(new RichLabelComponent());
            entity.AddRenderComponent(new LevelBadgeComponent());
            break;
        case EntityType.Monster:
        case EntityType.Boss:
            entity.AddRenderComponent(new LabelComponent());
            break;
        case EntityType.Npc:
            entity.AddRenderComponent(new LabelComponent());
            break;
    }
}
```

**EntityBase Facade 模式（外部调用方零改动）：**

组件化后，EntityBase 保留所有原有 setter 做转发，外部调用方（DebugPanel、Manager）不需要改调用路径：
```csharp
// EntityBase 保留 setter，内部转发给组件
// 组件在实体构造时就全部添加好（Factory 方法里），不存在"组件还没添加"的情况
public void SetHealthBarColor(Color color)
{
    GetRenderComponent<HealthBarComponent>()!.Color = color;
    QueueRedraw();
}
```

这样 DebugPanel 的 `monster.SetHealthBarColor(color)` 调用不用改，只是内部实现从直接写字段变成转发给组件。

**关键约束：** 渲染组件在实体构造时（Factory 方法）就全部添加好，setter 调用时组件一定已存在，不需要 pending 缓存。

## 5. 实施优先级与依赖

```
Phase 0 (文档) ← 当前
    ↓
Phase 1 (服务端基类+组件接口) ← 纯新增，可立即开始
    ↓
Phase 2 (服务端状态迁移) ← 依赖 Phase 1
    ↓
Phase 3 (协议统一) ← 依赖 Phase 2（需要组件数据结构确定）
    ↓
Phase 4 (客户端渲染组件化) ← 可与 Phase 1 并行开始
    ↓
Phase 5 (清理) ← 依赖 Phase 3 + Phase 4
```

**Phase 4 可以提前开始的原因：**
客户端渲染组件和服务端能力组件是两套独立系统。客户端根据 EntityType 就能决定渲染组件组合（Monster 有血条、NPC 默认隐藏血条），不需要等服务端下发组件列表。Phase 3 完成后再改成协议驱动即可。

**可以并行的：**
- Phase 1 + Phase 4 可以同时进行（服务端组件接口 + 客户端渲染组件接口）
- Phase 3 的协议定义可以在 Phase 2 进行中就开始

**不建议跳步：**
- Phase 2 不完成就做 Phase 3 → 协议字段不确定

## 6. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 服务端状态迁移遗漏字段 | 运行时属性丢失 | 逐字段对照表（第4节迁移映射），迁移完跑 restart.bat 验证 |
| 协议变更双端不同步 | 客户端解析失败 | 一次性替换，双端同时升级，git revert 可回滚 |
| 客户端渲染组件化引入内部 bug | 渲染异常、属性不同步 | Facade 模式保证外部接口不变，逐组件迁移+Godot 运行验证 |
| EntityBase 瘦身过度 | 子类需要大量 override | 保留必要的虚方法，组件只管渲染数据 |
| WorldState 一步到位替换导致编译错误多 | 改动面大，编译报错多 | 按方法逐个迁移，先改 FindEntityPosition 再改 IsOccupied，每步编译验证 |
