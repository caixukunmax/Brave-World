# 开发期服务器托管 + 客户端自动重连 设计文档

- 日期：2026-08-28
- 状态：待确认（确认后进入实现）
- 适用范围：仅开发期（editor / dev 构建），不影响导出发布版

## 1. 背景与目标

开发客户端时经常需要重启客户端，目前每次都要手动确认/启动服务器（`servercsharp/restart.bat`），体验割裂。

目标（按你的选择）：

1. **只为开发期省事**——不做可发布的离线/单机模式，不动权威服务器架构，不做传输层抽象。
2. **服务器"混合"形态**——平时由客户端自动拉起、隐藏托管；需要调试服务器时，你能把它单独拎出来（自己 `restart.bat` 起一个带日志/可附加的实例），客户端识别到已有服务器就直接连、绝不重复启动。

一句话：**客户端启动 → 若 8889 没人监听则自动拉起 GameServer → 连上；客户端重启 → 服务器不动、客户端自动重连。**

## 2. 现状（已核对）

- 架构：客户端(Godot) 与 服务器 是两个独立进程，仅通过 TCP 通信；两边只共享 protobuf（`Game` 命名空间），客户端不引用 `GameServer.GameLogic`。
- 客户端连接：`NetworkManager.Connection.cs` 里 `ConnectToServer()` 单次尝试，失败发 `ConnectionError`；`_Process` 检测到断线发 `Disconnected`。**均无自动重试/重连。**
- 连接地址写死：`ServerHost = 127.0.0.1`，`ServerPort = 8889`。
- 服务器：`GameServer.exe`（`servercsharp/src/GameServer/bin/Debug/net8.0/`），`build.ps1 dev` 会先杀旧进程→重建→`& $exe` 前台运行。

## 3. 方案设计

### 3.1 组件一：DevServerLauncher（客户端侧，dev-only autoload）

职责：在客户端启动时，确保有一个可用的服务器，并区分"托管"与"附加"两种模式。

启动流程：

1. **探测**：用一次带短超时（~200ms）的临时 TCP 连接探测 `127.0.0.1:8889`。
   - 连上 → **附加模式**：说明你已手动起了服务器（调试场景），客户端不启动新进程，直接复用；退出时也**不杀**它。
   - 连不上 → **托管模式**：拉起 `GameServer.exe`，记录其 PID，轮询端口直到就绪（带总超时，如 15s），再交给 NetworkManager 连接。
2. **托管的进程形态**（见决策点 D2）：默认隐藏控制台窗口后台跑；可选"可见窗口"模式方便盯日志。
3. **退出清理**：仅当本次是"托管模式"（自己 spawn 的）才在客户端退出时 kill 该 PID，避免遗留孤儿进程；"附加模式"绝不动别人的进程。
4. **工作目录**：spawn 时把服务器进程工作目录设为仓库根（与 `build.ps1` 里 `& $exe` 的 cwd 一致），确保服务器能找到 `data/tables` 等内容。实现时验证。

### 3.2 组件二：客户端自动重连（NetworkManager）

- 新增"自动重连"开关（dev 默认开）。当处于 `ConnectionError` 或 `Disconnected` 且未连接时，按固定间隔（如 1.5s）重试 `ConnectToServer()`，直到成功。
- 效果：你 `restart.bat` 重建/重启服务器时，客户端不用管，服务器一起来客户端就自动连回。
- **重连深度**（见决策点 D1）：断线重连后，服务端的 session/token 已失效。第一版建议**只自动恢复 TCP 连接并回到登录界面/用缓存 token 重新登录**，不做"无缝恢复到断线前的战斗/地图状态"（那需要服务端会话保持，超出"开发期省事"范围）。

### 3.3 生效范围与开关

- 仅在 **编辑器构建（editor_build）** 下启用 DevServerLauncher 与自动重连；导出发布版通过运行时开关彻底关闭（发布版连真实远端服务器，不该本地 spawn）。
- 判据用 `OS.HasFeature("editor_build")`，**不是** `"editor"`：autoload 跑在按 F5 启动的游戏进程里，该进程不带 `"editor"` 特性（那是编辑器进程自己的），用错会导致启动器在开发运行场景里永不触发。`editor_build` 在"编辑器二进制跑游戏"时为 true、导出模板为 false，正合适。

## 5. 边界与风险

- **不要重复起服务器**：靠"先探测端口再决定 spawn/attach"规避；探测超时要短，别拖慢启动。
- **孤儿进程**：客户端崩溃没走退出清理时，可能遗留 GameServer.exe。缓解：下次启动探测到端口被占即视为附加、不再 spawn；文档说明手动 `kill_gs.ps1` 兜底。
- **Godot 进程 API**：`OS.CreateProcess` 在部分导出模板/平台受限——但我们只在编辑器/dev 用，风险可控；实现时确认可用性与隐藏窗口参数。
- **线程模型**：spawn 与重连都在客户端主线程 `_Process` 里做，不涉及服务端 `IGameLoopScheduler` 约束。
- 本方案**不改 proto、不改服务端逻辑、不动权威边界**，符合"最小改动"。

## 6. 待你拍板的决策点

- **D1 重连深度**：断线自动重连后，第一版只做到"回到登录/用缓存 token 重新登录"够不够？还是你希望尽量恢复到断线前的场景？（推荐前者，简单且够用）
- **D2 托管服务器窗口默认形态**：默认隐藏后台跑（干净），还是默认弹一个可见控制台方便你随时盯服务器日志？（推荐隐藏，另给一个"可见/调试"开关）
- **D3 是否还要一个"一键起服务器+客户端"的独立脚本**：作为不通过客户端托管时的备选入口（比如你想先单独把服务器跑起来调试）。推荐顺手加一个，成本极低。
