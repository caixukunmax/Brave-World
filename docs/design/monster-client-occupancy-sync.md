# 怪物客户端占格同步

## 1. 背景

当前客户端在收到 `MonsterMoveNotify` 后，会立刻把怪物逻辑坐标切到 `to_x/to_y`，同时开始 tween 动画。

这会造成两个问题：

1. **视觉位置和逻辑位置分叉**
   - 画面上的怪物还在从 A 走向 B
   - 客户端逻辑却已经把它当成“到达 B”
2. **与服务端占格语义不一致**
   - 服务端移动期间仍保留怪物当前格
   - 同时对目标格做 reservation
   - 也就是“当前格 + 目标格”都会阻挡

于是玩家会看到：

- 怪物看起来还在原地附近
- 某些目标格却已经走不过去
- 调试面板里的单位坐标还可能显示成另一套缓存值

## 2. 目标

客户端怪物移动期间的语义与服务端保持一致：

1. 当前格在移动完成前仍然是怪物的正式位置
2. 目标格在移动完成前属于“预占格”
3. 调试显示要尽量区分“当前格”和“目标格/预占格”

## 3. 方案

### 3.1 Monster 实例

Monster 在开始移动时：

- 不立即改写 `GridX/GridY`
- 只启动从当前 world position 到目标 world position 的 tween

Monster 在 tween 完成时：

- 再正式提交 `GridX/GridY = target`

### 3.2 MonsterManager 占格

MonsterManager 拆成两类集合：

1. `occupied`
   - 当前正式占用格
2. `reserved`
   - 正在移动中的目标预占格

`IsBlockedByMonster()` 返回两者并集。

这样客户端阻挡逻辑会与服务端一致：

- 移动中的怪物，原格仍挡
- 目标格也挡

### 3.3 单位列表

单位列表不再直接读 `NetworkManager.Monsters` 的初始缓存作为“实时位置”，而是优先读场景中当前怪物实例：

- 静止怪：显示 `(x,y)`
- 移动怪：显示 `(x,y) -> (tx,ty)` 或增加“移动中”提示

## 4. 预期收益

- 视觉位置、阻挡语义、调试显示不再互相打架
- 客户端与服务端移动占格模型一致
- 排查“为什么这个格走不过去”时，不再被初始缓存坐标误导
